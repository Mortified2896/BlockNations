## Implementation plan

Development rule profiles now support the unchanged four-unit v4 baseline, `blocknations-simulation-v5-vision2` (four units, Archer vision 2), and `blocknations-simulation-v5-core3` (Warrior/Rider/Archer recruitment, Archer vision 2). The Python supervisor's `--rules-version` selects a new run's profile; Resume retains that run's recorded profile. Native workers and viewers receive the profile explicitly. Transfers preserve original trained-rules provenance and stable neural slots, and must advance training past the parent checkpoint before claiming a new-rules model. `Tools/Training/rule_profile_study.py` provides bounded matched continuations with fixed before/after evaluation and the same shared storage root. Human recordings are ingested only under matching rules. These experiments do not alter ordinary gameplay/PBp or authorize browser export; see the [balance experiment](AI_Balance_Experiment.md#completed-exploration-comparison-and-matched-rule-trials-2026-10-11) for current measurements and limits.

The installed `LocalTrainingBalanceV4.app` remains the baseline playtest/inspection build. New-profile human play requires a separately rebuilt native player; a mismatched player is rejected instead of silently running the wrong rules. The new profile worker lives in `Build/TrainingWorkerRuleProfiles`, preserving the running v4 binary.

Use Unity ML-Agents 4.0.x with the matching Python trainer 1.1.0. Keep Python dependencies in a project-specific environment outside Assets and generated results outside Git. The initial target is one visible two-seat 11×11 arena and a small numeric-observation policy.

Fair observations are projected from the shared match state for Hard and training. TurnManager's explicitly configured external path is bounded to development scenes and bypasses user save/resume, autosave and ordinary AI scheduling. Gameplay, saves and PBp retain their existing Unity/transport interfaces while their action transitions use the shared rules kernel.

Give each seat one learning Agent. Use an observation/action schema with unit and recruit statistics/capabilities, visibility/memory, and a stable two-stage source/action selection. Mask impossible choices from authoritative legal actions; no implicit actions outside the mask. The first schema supports the 11×11 board and a declared recruit roster capacity, with version checks for exported models. Hidden enemy information is never a policy input.

Use an isolated training scene with explicit references. Reset complete matches with a recorded seed, clear per-seat information memory, and request decisions only for the current owning seat. Genuine captures end both episodes with opposing win/loss rewards. Artificial round/action limits interrupt episodes and are recorded separately from wins/draws. Use a mixed curriculum: four in five openings start with varied roster units and nearby cities, increasing their distance after a 100-game capture-rate check; one in five uses the ordinary full opening. Curriculum episodes stop at 30 rounds, full openings at 100. Both use the full authoritative rules/action path. Capture rate measures task completion, not strength against a human or an existing opponent.

The current default is [decoupled C# training with a separate replay-first viewer](Decoupled_Training_Implementation.md). Independent arenas run outside Unity and feed one ML-Agents learner; the optional native viewer reads bounded recent-game records. Closing it leaves training running. The following native scheduling details describe the retained diagnostic fallback.

A native arm64 training player is also available for lower Editor overhead and unattended runs. The Editor remains the control surface; the standalone player renders the current board from cached authored sprite geometry. The direct backend does not recreate tiles, Units or health canvases on every match. `--training-simulation scene` selects the scene adapter for diagnostic comparison; both backends use the same rules. Status includes `simulationBackend` and `simulationVersion`. Direct training batches at most 16 decisions or 25 ms of work per rendered frame, yielding after the current decision; Python/RPC stalls can still take longer. Human/offline playtests retain their existing scheduling. Unity CLI validation uses an isolated project snapshot when the live Editor cannot refresh, never a second Editor against the same checkout.

An Editor training window launches the local Python supervisor. With **Decoupled C# training**, choose 1/2/4 parallel games and optionally watch the standalone viewer; it defaults to recent replays. **Watch live training → All 4 games** shows four sampled boards in a 2×2 grid, with **Focus** returning to one arena. Live snapshots publish at a fixed 2 Hz through a bounded background mailbox regardless of viewer state; the simulation never waits for a displayed frame. The 15 fps viewer uses lower scheduling priority, although it still shares hardware resources with learning. See the [decoupled implementation](Decoupled_Training_Implementation.md) for limits and validation. The fallback launches the wired scene directly. Successive matches need no confirmation. Include Start/Resume/Stop, duration, seed, storage used/limit/free space, games/actions/rate, checkpoint/model selection, and local inference playtesting. Pin user-selected models and preserve the latest resumable checkpoint.

The supervisor owns an editable total 20 GB budget across training runs, bounded logs, checkpoint retention, reserved write space, a free-disk guard, and graceful shutdown. Keep the latest checkpoint and active inputs; remove only eligible generated artifacts in owned run directories. Use a temporary macOS system-sleep assertion tied to the run, support screen locking, and restore background execution when leaving training. Keep the lid open and power connected for overnight runs.

ML-Agents can reset the environment when switching the self-play training seat. Discard that partial match and its in-flight decision, clear seat knowledge/source selection, and start a fresh authoritative board on the next frame. Record trainer resets separately from completed matches and capture rewards. Batch validation/build Editors must not adopt or stop an independently running training session through shared Editor preferences.

## Using the controls

Open **Tools → Block Nations → Local ML Training → Open Controls**. Set the board size, maximum hours, storage limit, seed, and curriculum. **Start New Training** automatically creates a unique ID containing the board size and UTC timestamp, starts with random weights, launches successive matches, and opens the current board. It keeps the new ID selected under **Saved run ID** for a later resume; that field does not affect starting fresh. Existing run directories and files are skipped when generating an ID, even if two launches occur in the same second. This is not a tournament or a per-match selection flow. The window shows supervisor status, storage/free space, checkpoint counts, live match statistics, decisions/second, rejected actions, and sampled peak resident memory of the trainer/player processes.

For unattended Mac runs, first use **Build Mac Training Player**, then enable **Use standalone training player** and point it to `Build/LocalTrainingV2.app`. The same Unity window starts/stops the run; the separate player shows the live training board. Editor mode remains available. Background execution is enabled for training, so locking the screen does not pause the match loop. The launcher owns `caffeinate -i -s -w <supervisor pid>` without a display assertion and releases it at the end. Unity's native player may independently keep an idle display awake; manual screen locking is supported. Keep the Mac plugged in with its lid open and leave the training applications running; quitting the control Editor requests a stop. No system power preferences are modified.

**Stop and Save Checkpoint** requests graceful trainer shutdown, including for a zero-hour run. Click it once and wait through `saving` until **Trainer** shows `stopped / user_stop` before closing Unity or the training player. This saves resumable weights and exports the policy. **Pause live run** pauses gameplay while keeping the session open; use the stop button to finish it. **Resume Saved Run** uses **Saved run ID** and continues its network/optimizer/trainer configuration, original board size, seed, and curriculum stage, regardless of the new-run board dropdown. The most recently launched ID stays selected by default. Episode counters restart for each launch; the current partial game is not restored. Select a numbered `.onnx` checkpoint and press **Play Against This Model** after stopping training. This uses a fresh full opening, ordinary human inputs, and local CPU inference without Python. Imported models and their available resumable weights are copied to a content-addressed `pinned/` archive outside ML-Agents' own retention directory. The local imported asset is ignored by Git.

**Maximum hours = 0** enables continuing learning without a wall-clock limit for a new or resumed run. The storage ceiling, free-disk guard, manual stop, trainer failures, and graceful checkpoint saving remain active. Retention reuses storage by removing eligible old artifacts; the 20 GB allowance is a maximum across runs, not a target to fill, and an open-ended run may keep running for a long time below it. These settings apply when launching/resuming, not to an already running session. The controls show the actual session time limit and trainer step plan; elapsed hours do not wrap at 24.

The finite trainer normally ends at one million cumulative learning steps and anneals its learning rate, PPO entropy coefficient, and clipping parameter toward that endpoint. The first zero-hour launch changes that run to continuing learning: the same network, rewards, optimizer checkpoint, nominal parameter values, opponent pool settings, and checkpoint interval are retained, while those three schedules become constant. The exact prior trainer configuration is preserved in `trainer-before-continuous.json`. ML-Agents requires a finite integer step limit, so its internal bookkeeping uses an exactly representable ceiling of 2^62 steps, billions of years beyond the measured throughput. This removes the practical hidden step stop rather than leaving the one-million-step cap active. Continuing learning remains the run's trainer plan on future resumes; a later positive hour value can still stop a session on time. New runs with positive hours keep the original finite plan.

The default Mac storage root is `~/Library/Application Support/BlockNations/Training`. Its 20 GB limit is shared across all owned runs, including checkpoints, pinned models, metrics and logs. Experience buffers live in RAM; full action/snapshot/video archives are disabled. The supervisor stops at 19.488 GB to leave a 512 MB final-write reserve, or earlier if the disk has less than 20 GB plus that reserve free. This is a supervised limit with two-second checks, not a filesystem quota. The small fixed network/buffers and bounded checkpoint/log settings keep normal writes far below the reserve. Python installation, Unity caches, and the built player are outside this training-artifact budget.

The initial policy had schema version 1; the current schema is version 2. Both use a two-seat 11×11 canvas, 3,120 numeric observations, a 259-choice two-stage source/action interface, and up to 16 recruit definitions. Smaller supported boards are embedded in that canvas. It uses capabilities/costs rather than unit-name features. New abilities that need new observations/actions, a larger board, or a larger recruit roster require an explicit schema version and retraining. These are declared MVP limits, not permanent product/player/team limits. The shared rules kernel is implemented; a stronger policy, stable held-out evaluation and multiple parallel arenas remain follow-ups.

Starting city locations are public policy inputs. Enemy gold, hidden live units, stable unit identities, enemy action counters and enemy recruitment flags are excluded. The last two were removed during the shared-simulation extraction even for visible enemy units. Tensor dimensions remain compatible with saved schema-2 weights, but their information distribution changes and continued training is appropriate. Training rounds count complete cycles from the randomized first seat; supported product/PBp save numbering remains anchored to seat zero.

### Live training rating and seat outcomes

The spectator chart displays **Match-result Elo** from authoritative completed game events, beginning a new corrected history at 1200 in `match-elo.json`. Its horizontal axis is rated matches, starting with a 0–1,000 range and expanding in 1,000-match increments; the result line ends at the latest recorded match rather than filling the chart immediately. The legacy `training-elo.json` trajectory curve is retained but no longer displayed or appended. Older inflated ratings are not imported. This remains relative to training opponents, not human Elo or a fixed evaluation benchmark.

`TrainingMatchJournal` records opening and terminal results independently of Agent decisions, including a capture before the losing seat acts. A pinned ML-Agents 1.1.0 adapter replaces only trajectory-based Elo processing; PPO trajectories, rewards, and stock opponent selection remain in place. It identifies both policies by hashes of their actual weights. Elo uses K=16 and symmetric updates; identical weight hashes are the same rated entity and cannot gain Elo from playing themselves. New learner revisions inherit the preceding training rating; snapshots retain their own identities. This is a training estimate across evolving versions, not a frozen checkpoint league.

Every terminal event is counted once using session/sequence identities, persisted with the corrected history. Limits are interruptions, not draws. Matches whose policy identities changed between opening and terminal state are counted as unrated and shown explicitly; partial SDK resets are abandoned, not losses. The adapter preserves pending opening metadata across saves and refuses sequence gaps or invalid protocols. Journal storage is bounded to two 8 MB files; chart history retains at most 200 samples across the whole recorded run, using minimum/maximum samples in time buckets that widen as the run grows. The baseline, latest result, and each bucket's extrema survive compaction; active model identities and 128 session cursors are also retained. Weight hashes are cached against Tensor mutation versions to avoid copying unchanged networks on each decision. Installed SDK files are never edited; upgrading ML-Agents requires an adapter compatibility audit.

When resuming that data, additive curve metadata records the first surviving match; the chart shows that recorded window and labels earlier samples unavailable. Lost ratings are not interpolated or reset. New runs retain coverage from match zero. The faint dashed line marks the starting rating; the mint line shows measured samples. This changes development telemetry only, preserving rating values, trained weights, product saves, and PBp formats.

### Spectator fog views

Live training and recent-match inspection share a **Shared / Blue / Red / All** vision selector, defaulting to Shared. Shared reveals the union of both seats' current sight: dark tiles are unseen by either seat. Blue and Red show only that seat's current visible tiles and conceal units outside them. These individual views are better for inspecting scouting and surprise attacks. All preserves the omniscient view.

Replay frames capture independent visibility masks through the same read-only `ComputeVisibilityForSeat` rules used by seat observations. The viewer draws copies over the camera; it never mutates game visibility, legal actions, observations, or rewards. Fog remembers no explored tiles in this viewer: it depicts current sight. Public starting city coordinates remain marked with a neutral City label under fog, without revealing hidden current ownership. Yellow means movement remains for the active seat; when movement is exhausted, a smaller attack marker appears only if an attack remains and a target is legal in that seat's vision. ### Cumulative training time

Both live and replay sidebars display **Total training: HH:MM:SS** for the current run's weight lineage. The supervisor persists `training-time.json` independently of each launch's duration budget. It accumulates connected, unpaused, healthy trainer intervals on the existing two-second polling loop; stopped time, setup, and replay viewing with live training paused are excluded. Watching a replay while training continues counts normally. Resuming restores the total; a fresh run starts at zero. This reports elapsed active training time, not CPU/GPU utilization or a playing-strength metric.

Legacy runs recover an approximate baseline from retained ML-Agents Time Elapsed summaries, summing sessions when their elapsed clock resets. The overlay marks these totals with ≈ and explains that earlier sessions are estimated. Historical pauses, time after the last summary, and rotated-away logs cannot be reconstructed exactly. The recovered baseline is stored once, so subsequent resumes do not re-add the logs. Telemetry is scoped to run id and board size and never enters policy observations, rewards, saves, or PBp data.
